# This repo

Personal site. Frontend lives in `frontend/` (React 19 + Vite + TypeScript + Tailwind v4).

> **Current status**: v3.1. All four pages (`/`, `/projects`, `/scratchpad`, `/contact`) are
> hand-designed and finished. v2 added a Supabase backend: live Spoin topics, threaded
> comments with both page-level and per-comment likes, session-deduped view counts, and
> build-time metrics pulled from the database, across every Scratchpad category, not just
> writeups. v3 made the layout work on every screen, from a 280px folding phone up to a
> desktop monitor, where before it was built for a PC only. See `README.md` for the full
> backend rundown, the CLI tools for managing it, and how the responsive system fits
> together.

Design direction: warm dev-log terminal aesthetic, dark plum/amber palette, IBM Plex Mono,
dense list-based sections, small line icons, no big hero graphics. See
`frontend/src/index.css` for the token system (`--color-*` under `@theme`).

Responsive rules: mobile-first, with a custom `xs` tier at 380px for small phones and folds,
`sm` at 640px splitting narrow from wide, and a page-level `zoom` above 880px. Anything new
has to hold from 240px up. When a row runs out of width, wrap it or restructure it, do not
scale the type down to fit: the site already sits at its legibility floor. The zoom brings
two gotchas: `100vh` stays the unzoomed viewport (so no `min-h-screen`), and
`getBoundingClientRect` reports zoomed pixels. `index.css` explains both where the rule lives.

Real content only. Project facts, ADR dates, and experience come from
`frontend/src/content/` and `frontend/src/data/synced-docs.json` (the latter generated by
`npm run sync-docs`, sourced from local ADR/architecture markdown outside this repo, see
`frontend/content/manifest.json`).

## Writing style for site copy

This is a personal website, not a resume. All copy (project descriptions, bios, log entries,
UI text) should sound like the person talking, not like resume bullet points.

- No em dashes anywhere on the site or in this doc. Use a period, a comma, or restructure the
  sentence instead.
- Avoid resume-verb openers ("Engineered...", "Architected...", "Spearheaded...",
  "Constructed an end-to-end..."). Say what the thing does and why it exists, plainly.
- Avoid corporate/AI-slop phrasing: "leverage", "seamless", "robust solution", "cutting-edge",
  semicolon-joined bullet fragments, and other stock LLM tics.
- Ground every fact in something real (repo READMEs, code, ADRs, commit history). Do not
  invent metrics, thresholds, or "what broke" stories that cannot be traced to an actual
  source. When unsure, say less rather than fabricate a specific-sounding detail.
- Contractions and a direct, first-person-adjacent tone are fine. Write it the way you'd
  explain it to another engineer, not the way you'd summarize it for a recruiter.
